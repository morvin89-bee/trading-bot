## Butir 4 — sumber `fee_pct = 0.002` (hanya laporan, tidak diubah)

Nilai `0.002` berasal dari **hardcode** di tiga tempat, bukan dari bursa:

- `proposal.FEE_PCT = 0.002` — dipakai pesan konfirmasi
  (`proposal.confirmation_text`) untuk baris "Perkiraan fee 0,2%".
- `rules.take_profit_actions(fee_pct=0.002)` — dipakai menghitung untung
  **neto** sebelum ambang take-profit.
- `rules.rebalance_actions(fee_pct=0.002)` — dipakai saat rebalance

Angka itu adalah **fee taker 0,2%** dalam bentuk fraksi.

Perbandingan dengan metadata pair resmi (`https://indodax.com/api/pairs`,
diambil 2026-11-10):

|---|---|---|
| `trade_fee_percent` | `0.2` | persen -> fraksi `0.002` |
| `trade_fee_percent_taker` | `0.2` | persen -> fraksi `0.002` |
| `trade_fee_percent_maker` | `0.1` | persen -> fraksi `0.001` |

Kesimpulan: **konsisten** dengan fee taker. Tidak ada perubahan kode.

ambang, dengan cadangan `proposal.FEE_PCT` bila metadata hilang. Jangan

mengubah parameter strategi, dan angka taker 0,2% saat ini justru

## Butir 5 — `preflight --target bayangan|live`

- `python -m preflight` tetap default `live` (menuntut `shadow_day >= 7`).
- `python -m preflight --target bayangan` menjawab "boleh mulai mode
  bayangan?": lantai hari **tidak** dipersyaratkan, tetapi `v1_enabled`
  harus 0 (sakelar nyala = bukan target bayangan).
- Hasil tiap pemeriksaan kini tiga keadaan: `OK`, `GAGAL` (dievaluasi dan
  gagal), `TAK TERBACA` (DB tidak terbuka, izin `None`, jam bursa gagal
  dibaca). Kode keluar: `0` GO, `1` NO-GO (menang atas 2), `2` tidak bisa
  dievaluasi.
- `client_order_id` ditambahkan ke kolom `proposals` yang diperiksa, supaya
  DB yang belum dimigrasikan tidak lolos preflight lalu gagal saat
  pemulihan usulan.
- Keluaran tidak memuat nilai kunci API; tes memeriksa ini.

### DECISIONS FOR ME

1. **`--target bayangan` menolak `v1_enabled = 1`.** Saya memilih ini agar
   preflight bayangan tidak memberi lampu hijau saat sakelar eksekusi sudah
   menyala. Bila Anda ingin preflight bayangan tetap lolos dalam kondisi
   itu, cukup hapus cabang `switch_on` pada `target == "bayangan"`.
2. **`TAK TERBACA` = kode 2, bukan 1.** Artinya "jangan nyalakan sakelar,
   tapi perbaikannya beda": buka DB/perbaiki izin/jaringan, bukan parameter
   strategi. Bila Anda lebih suka semua non-GO = 1, satu baris di `main`
   perlu diubah.

# Putaran 3 (2026-11-11): metadata, DCA, bukti presisi, urutan go-live

## Butir 1 — refresh metadata tidak lagi diam dan tidak lagi tiap tick

**Temuan.** `main_loop.tick_cycle` memakai `try: pair_meta.refresh(...)
except Exception: pass`. Kegagalan jaringan hilang tanpa jejak, dan karena
percobaan gagal tidak menulis cap waktu, setiap denyut (5 menit) mencoba
jaringan lagi.

**Frekuensi sebelum perbaikan.** Sukses: paling banyak 1×/24 jam
(`MAX_AGE_S`). Gagal: setiap denyut = 288 percobaan/hari.

**Perbaikan.**
- `pair_meta.RETRY_S = 900`: percobaan (sukses maupun gagal) dicap di tabel
  `pair_meta_state` SEBELUM jaringan, jadi kegagalan beruntun maksimal
  1×/15 menit = 96 percobaan/hari.
- Kegagalan dicatat lewat `_catat_denyut_dilewatkan` yang sudah menyamarkan
  token (`_samarkan_pesan_galat`), bukan `pass`.
- Pengguna diberi tahu **sekali per hari** hanya bila `pair_meta.umur_tertua`
  melewati `MAX_AGE_S` (atau metadata belum ada). Kegagalan percobaan ulang
  saat cache masih segar tidak memicu alarm.
- `preflight` memeriksa "metadata pair segar" untuk semua koin yang dilacak;
  hilang/basi = NO-GO, karena engine pasti halt pada keadaan itu.

**Usulan TTL (belum diubah).** Pertahankan `MAX_AGE_S = 86400` (batas halt),
tetapi segarkan lebih awal, mis. `SEGARKAN_S = 6 * 3600`, dengan alasan:
`trade_min_traded_currency` bersifat dinamis, sehingga metadata berumur 24
jam bisa memuat minimum yang sudah bergeser. Menyegarkan tiap 6 jam memberi
margin 18 jam sebelum halt dan hanya 4 panggilan publik/hari. Belum
diterapkan karena mengubah beban jaringan dan ambang halt adalah
keputusan Anda.

## Butir 3 — bukti arti field presisi per pair

Sumber (semua read-only, tanpa kunci API, diambil 2026-11-11):

1. Dokumentasi resmi `Public-RestAPI.md`
   (`https://github.com/btcid/indodax-official-api-docs`), bagian

   `quantity_increment: "0.00000001"`,
   `trade_min_base_currency: 50000`,

   `trade_fee_percent: 0.2`.
2. Panggilan `GET https://indodax.com/api/pairs`.
3. Panggilan `GET https://indodax.com/api/ticker_all` (untuk membandingkan
   minimum koin dengan harga terakhir).

Hasil `/api/pairs` saat pengambilan:

| pair | `quantity_increment` | `trade_min_base_currency` | `trade_min_traded_currency` | `trade_fee_percent` |
|---|---|---|---|---|
| `btc_idr` | `1e-08` | `10000` | `7.47e-06` | `0.2` |
| `eth_idr` | `1e-08` | `10000` | `0.00026859` | `0.2` |
| `sol_idr` | `1e-08` | `10000` | `0.00656655` | `0.2` |
| `bch_idr` | `1e-08` | `10000` | `0.00240096` | `0.2` |

Bukti bahwa `trade_min_traded_currency` **dinamis** (bukan minimum koin
tetap): `min_traded * harga_terakhir / min_base` =

| pair | rasio |
|---|---|
| `btc_idr` | 1,0002 |
| `eth_idr` | 1,0000 |
| `sol_idr` | 1,0016 |
| `bch_idr` | 1,0000 |

Rasio ≈ 1 berarti minimum koin adalah ekuivalen koin dari minimum IDR pada
harga terakhir. Karena itu:

- `quantity_increment` = langkah qty terkecil yang diterima bursa; qty
  harus kelipatan nilai ini. Kode menyimpan apa adanya lalu
  `Decimal(str(...))` — aman untuk bentuk string (`"0.00000001"`) maupun
  angka JSON (`1e-08`).
- `trade_min_base_currency` = minimum nilai order dalam IDR.
- `trade_min_traded_currency` = minimum qty koin, **dihitung bursa dari
  minimum IDR dan harga**; bukan ambang independen. Pemeriksaan engine yang
  memakai keduanya tetap konservatif: `qty_bulat * price_ref` vs min IDR
  dan `qty_bulat` vs min koin. Bila `price_ref` (limit) lebih rendah dari
  harga terakhir, cek koin bisa lebih ketat — arah yang aman (menolak),
  bukan melebihkan order.
- `trade_fee_percent` = persen; `0.2` = 0,2% = fraksi `0.002`, sama dengan
  `proposal.FEE_PCT`. `trade_fee_percent_taker` juga `0.2`;
  `trade_fee_percent_maker` `0.1`.

Catatan: contoh di dokumentasi (`50000`, `0.0001`) **berbeda** dari nilai
live (`10000`, `7.47e-06`). Karena itu kode tidak boleh menghafal contoh
dokumentasi; `pair_meta` memakai nilai live dan halt bila tidak tersedia.
Tidak ada perubahan kode pada butir ini.

## Butir 2 — urutan go-live diverifikasi; satu langkah memang mustahil

Bukti: `test_urutan_golive_preflight_di_tiap_langkah` menjalankan preflight
pada tiap keadaan urutan:

| keadaan | preflight live | preflight bayangan |
|---|---|---|
| awal: bot mati, kunci baca-saja, sakelar 0 | GO | GO |
| kunci trade dipasang, sakelar masih 0 | **GAGAL (izin kunci)** | GAGAL (izin kunci) |
| kunci trade + sakelar nyala bersamaan | GO | GAGAL (mode) |
| dibatalkan: `set_shadow_day(0)` + kunci baca-saja | GO | GO |

**Temuan.** Urutan lama §0 ("pasang kunci trade → preflight live →
`aktifkan_live`") memaksa preflight GAGAL di langkah tengah, karena
`permissions_ok` menuntut `canTrade == switch_on`. Itu bukan bug preflight:
`main_loop.tick_cycle` memakai aturan yang sama (`switch_on=not shadow`), jadi
kunci trade + sakelar mati memang halt di runtime.

**Perbaikan (dokumen, bukan kode).** §0 langkah 4–5 diurutkan ulang:
preflight live dengan kunci baca-saja → kunci trade + `aktifkan_live`
bersamaan (bot masih mati) → preflight live sekali lagi → baru bot
dinyalakan; bila preflight kedua gagal, `set_shadow_day(0)` + kembalikan
kunci baca-saja. Jendela "sakelar nyala, bot mati" tidak bisa mengirim order.

Ikut diperbaiki karena bertentangan dengan aturan yang sama: §3 checklist
dulu menyatakan "kunci bayangan dan live sama dengan izin yang sama" —
sekarang baca-saja untuk bayangan, trade-only untuk live.
